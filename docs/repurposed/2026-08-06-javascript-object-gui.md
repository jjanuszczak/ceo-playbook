## LinkedIn

### Option 1

JavaScript Object GUI is a project I started thinking about in 2008 and can now finally build properly.

The idea is simple:

- Build browser applications with JavaScript objects.
- Set properties.
- Add controls to containers.
- Wire explicit events.
- Keep state and validation readable.

No HTML-first mental model. No direct DOM plumbing in application code.

This is not a React replacement. It is a narrower bet: internal tools, CRUD-heavy systems, and form-heavy business applications should often feel more like desktop software than page construction.

So what?

AI-assisted coding does not remove the need for product judgment. It lowers the cost of scaffolding enough that smaller, sharper tools become viable again.

https://januszczak.org/lab/javascript-object-gui/

### Option 2

AI coding has changed the economics of niche software tools.

In the past, building a small custom UI framework meant carrying too much surface area by hand:

- Runtime
- Controls
- Examples
- Documentation
- Tests
- Release flow
- Roadmap discipline

Now the scaffolding cost is lower.

But the standard has to stay high. JavaScript Object GUI is my experiment in that direction: an object-first browser UI framework for internal tools and line-of-business applications.

So what?

The opportunity is not to build more vague platforms. It is to build sharper tools with tighter boundaries.

https://januszczak.org/lab/javascript-object-gui/

### Option 3

Most frontend work starts from pages.

JavaScript Object GUI starts from applications.

That difference matters when the target is not a public website, but a work surface people use all day:

- Admin consoles
- Opportunity boards
- Planning tools
- Form-heavy workflows
- CRUD systems

JOG uses a desktop-style model: controls, containers, stores, events, validation, dialogs, tabs, grids, and explicit binding.

The browser still renders the DOM. The developer works at the object layer.

So what?

For some internal software, the right abstraction is not another page framework. It is a control system that makes the business workflow easier to reason about.

https://januszczak.org/lab/javascript-object-gui/

### Option 4

JavaScript Object GUI is intentionally not trying to be a broad frontend platform.

That constraint is the point.

The first target is narrow:

- Desktop-style browser applications
- Internal tools
- Form-heavy operations systems
- CRUD-heavy workflows
- Developers who prefer controls and containers over markup-first composition

That is also why the project is still honest about its pre-release status. The model is useful, but the hardening work matters: accessibility, keyboard behavior, shell controls, grids, third-party control contracts, and packaging.

So what?

The future of AI-assisted software work may not be one giant framework for everything. It may be smaller tools with sharper contracts, built for specific jobs.

https://januszczak.org/lab/javascript-object-gui/
